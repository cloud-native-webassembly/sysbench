# Feature Detail: WAMR Runtime Backend

**Feature ID**: 003  
**Name**: WAMR Runtime Backend  
**Description**: Integrates the WebAssembly Micro Runtime SDK as a sysbench WASM backend, including memory address translation.  
**Status**: Implemented  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

WAMR (WebAssembly Micro Runtime) is the reference backend for this fork and the default
value of `--wasm-runtime`. It is the most complete of the four integrations: it is the only
backend that implements host↔sandbox address translation, which makes it the only one that
can currently support buffer-passing workloads. It therefore doubles as the proving ground
for the abstraction layer — the vtable shape in Feature 002 was validated against WAMR
first.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. All seven vtable members
are populated (`src/sb_wamr.c:167-174`) and every function has a real body. Two defects:
`sb_wamr_destroy` (`src/sb_wamr.c:56`) returns `SUCCESS` without releasing the module,
instance, exec env, or pooled heap; and `wasm_runtime_full_init` is called once per sandbox
inside `sb_wamr_create_sandbox` (`src/sb_wamr.c:124`) rather than once per process, so a
multi-threaded run re-initialises global runtime state per thread.

## Key Changes

1. Implemented the private context `sb_wamr_sandbox_context` (`src/sb_wamr.c:40-44`) holding
   `wasm_module_t`, `wasm_module_inst_t`, and `wasm_exec_env_t`.
2. Implemented `sb_wamr_create_sandbox` (`src/sb_wamr.c:108`) covering the full lifecycle:
   pooled heap allocation, `wasm_runtime_full_init`, `wasm_runtime_load`,
   `wasm_runtime_instantiate`, `wasm_runtime_create_exec_env`.
3. Implemented `sb_wamr_function_apply` (`src/sb_wamr.c:70`) using
   `wasm_runtime_lookup_function` + `wasm_runtime_call_wasm_a`, marshalling one `WASM_I64`
   argument and validating that the result kind is `WASM_I64`.
4. Implemented `sb_wamr_function_available` (`src/sb_wamr.c:98`) so the generic layer can
   probe for optional exports such as `create_buffer`.
5. Implemented address translation via `wasm_runtime_addr_app_to_native`
   (`src/sb_wamr.c:62`) and `wasm_runtime_addr_native_to_app` (`src/sb_wamr.c:67`) and wired
   both into the sandbox (`src/sb_wamr.c:160-161`) — unique among the four backends.
6. Registered the `wamr_vm` descriptor with `load_module = NULL` to reuse the shared file
   loader, and exposed `create_wamr_runtime()` (`src/sb_wamr.c:176`).

## Implementation Notes

- SDK surface used: `wasm_c_api.h` and `wasm_export.h`. Memory strategy is
  `Alloc_With_Pool` over a `malloc`'d buffer sized by `module->heap_size`.
- `init_args.instance_port` is set to `4000 + thread_id` (`src/sb_wamr.c:121`), which binds a
  per-thread port. This is a debug-server artefact and will collide with unrelated services
  or across concurrent sysbench runs.
- Execution mode is whatever `wasm_runtime_full_init` defaults to (classic interpreter in a
  stock WAMR build). There is no AOT or JIT selection, so numbers from this backend are not
  comparable to an AOT-compiled configuration.
- Error handling is disciplined: every failure path logs via `log_text(LOG_FATAL, ...)` and
  `goto error`, returning `NULL` / `FAILURE` rather than aborting. WAMR exception text is
  surfaced through `wasm_runtime_get_exception` (`src/sb_wamr.c:92`).
- `heap_base` is set to the pooled heap buffer (`src/sb_wamr.c:157`), giving the host a
  handle on sandbox memory.
- Status was derived from source inspection during registry bootstrap, not from a completed
  `/speckit.plan` → `/speckit.implement` cycle.

## Future Evolution Suggestions

- Move `wasm_runtime_full_init` to a process-wide init in `sb_wamr_init` and keep only
  load/instantiate per sandbox; this is both a correctness and a measurement-integrity fix.
- Implement real teardown in `sb_wamr_destroy` (deinstantiate, unload, destroy exec env,
  free pooled heap) — tracked as Feature 012.
- Make the debug `instance_port` opt-in rather than always-on, or derive it from a
  configurable base.
- Expose WAMR execution mode (interpreter / fast-interp / AOT) as a benchmark dimension so
  the backend can report which mode produced a result.
