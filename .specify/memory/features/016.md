# Feature Detail: Pinned SDK Provisioning

**Feature ID**: 016  
**Name**: Pinned SDK Provisioning  
**Description**: Reproducible, version-pinned acquisition of the four WASM SDKs and the WASI guest toolchain (DFCfg).  
**Status**: Draft  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

Five external toolchains gate this project: the four runtime SDKs and WASI-SDK for building
guest modules. None is vendored, version-checked, or installable from the repository. A
contributor must assemble all five by hand, and whatever versions they happen to install
silently become part of every benchmark result they produce.

That is a reproducibility problem before it is a convenience problem: WASM engine performance
changes substantially between releases, so an unpinned SDK makes results incomparable across
machines and across time. The constitution's WASM Runtime Harness Standards require exactly
this pinning.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. `third_party/` vendors only
`cram`, `luajit`, and `concurrency_kit` — no WASM SDK, and no `.gitmodules` at the repository
root. `m4/sb_wasm.m4` discovers SDKs by locating a CLI binary (`iwasm`, `wasmedge`, `wasmer`,
`wasmtime`) and derives include/lib paths by convention, with no version assertion anywhere.
`scripts/env.rc` consumes `LLVM_HOME`, `GCC_HOME`, and `WABT_HOME` without defining them, and
`src/wasm/Makefile.am` requires `WASI_SDK_HOME` with no stated version.

## Key Changes

1. Add a single provisioning script that installs all four runtime SDKs plus WASI-SDK at
   explicitly pinned versions into a known prefix, and emits the `*_HOME` exports that
   `m4/sb_wasm.m4` and `src/wasm/Makefile.am` consume.
2. Record the pinned versions in one declarative manifest so the pin is reviewable in a diff
   rather than buried in shell.
3. Add minimum-version assertions to each `AX_CHECK_*` macro so a too-old SDK fails configure
   with a clear message instead of failing to compile.
4. Define and document `LLVM_HOME`, `GCC_HOME`, `WABT_HOME`, and `WASI_SDK_HOME` in
   `scripts/env.rc`, validating that each resolves before use.
5. Replace CLI-presence discovery with a compile-and-link probe against each SDK's header and
   library, so a runtime CLI without development files is correctly reported as unusable.
6. Surface the resolved SDK versions into the run provenance record consumed by Feature 013.

## Implementation Notes

- Prefer download-and-verify (pinned release archive plus checksum) over git submodules for
  the runtime SDKs: the SDKs are large, and building WAMR, Wasmer, Wasmtime, and WasmEdge
  from source in every clone would dominate build time. Vendoring sources is the wrong
  trade-off here.
- WASI-SDK pinning matters as much as the runtime pins, because the guest module bytes — and
  therefore what every engine executes — depend on the clang version that produced them.
- The provisioning script must be idempotent and must not require root, so it works both on a
  developer machine and in the Feature 015 CI jobs with a cache.
- `-Wl,-rpath` baked in by `m4/sb_wasm.m4` means the built binary is tied to the SDK path
  chosen at configure time; a stable, documented prefix avoids surprising breakage when a
  developer moves an SDK.
- Pinning is a prerequisite for Feature 013's comparability claims and for Feature 015's
  cacheable CI, so this feature should land before either is finished.

## Future Evolution Suggestions

- Track "SDK version bump" as a deliberate, measured event: re-run the reference workload
  before and after so the engine's own performance change is recorded rather than confounded
  with project changes.
- Consider a container image carrying all five toolchains as the fastest path to a working
  environment, with the provisioning script as the source of truth for its contents.
- Add an `--wasm-sdk-versions` style diagnostic that prints what the binary was built
  against.
