# Feature Detail: WASM Test Type Dispatch

**Feature ID**: 001  
**Name**: WASM Test Type Dispatch  
**Description**: Registers `--type=wasm` as a first-class sysbench test type and selects a runtime backend via `--wasm-runtime`.  
**Status**: Implemented  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

Upstream sysbench dispatches a benchmark run to one of three backends: builtin C tests, Lua
scripts, or Python scripts. This feature adds a fourth backend — WASM — so that a `.wasm`
module can be driven by the same event loop, thread pool, timer, and statistics machinery
that the database and OS benchmarks use. It is the entry point for the entire WASM effort:
without it, no runtime backend is reachable from the command line.

The dispatch is two-level. `--type=wasm` selects the WASM backend; `--wasm-runtime=<name>`
selects which of the four supported engines executes the module. This keeps the runtime
choice orthogonal to the workload choice, which is what makes cross-runtime comparison
possible at all.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. Dispatch is functional
for `wamr` and `wasmedge`. Selecting `wasmer` or `wasmtime` resolves a runtime descriptor
whose `create_sandbox` pointer is never assigned, so the run reaches
`sb_wasm.c:231` and dereferences a NULL function pointer. Unknown runtime names are
rejected cleanly at `sb_wasm.c:114`.

## Key Changes

1. Added `--type` option accepting `'lua','python','wasm' or 'builtin'` and `--wasm-runtime`
   accepting `'wamr','wasmedge','wasmer' or 'wasmtime'` to `general_args[]` in `src/sysbench.c`.
2. Added `sb_load_wasm(testname, runtime)` in `src/sb_wasm.c:89` as the backend entry point,
   mirroring `sb_load_lua` / `sb_load_python`.
3. Added `sb_wasm_runtime_name_to_type()` in `src/sb_wasm.c:58` mapping a runtime name string
   to the `sb_wasm_runtime_t` enum declared in `src/sb_wasm.h:28`.
4. Registered `wasm_ops` (`src/sb_wasm.c:45`) into the `sb_test_t` operations table so the
   generic event loop drives WASM runs.
5. Added `SB_REQ_TYPE_WASM` request type and the `wasm_request` carrier field to the
   sysbench event union so a WASM call can travel through `next_event` / `execute_event`.

## Implementation Notes

- Backend selection is a `switch` over `sb_wasm_runtime_t` guarded by `#ifdef HAVE_WAMR`,
  `HAVE_WASMEDGE`, `HAVE_WASMER`, `HAVE_WASMTIME` (`src/sb_wasm.c:92-117`). A runtime that
  was not compiled in falls through to the `default` arm and is reported as unsupported,
  which is the correct behaviour.
- `--wasm-runtime` defaults to `wamr`, so a bare `--type=wasm` run exercises the most
  complete backend.
- The module path arrives as the positional test name and is stored in `sbtest.lname`
  (`src/sb_wasm.c:118-125`); a missing path is a fatal error rather than a crash.
- Only `EVENT_FUNC` (`"event"`) and `"create_buffer"` are actually invoked. The other nine
  hook-name macros defined at `src/sb_wasm.h`-adjacent lines in `src/sb_wasm.c:26-36`
  (`prepare`, `cleanup`, `help`, `thread_init`, `thread_done`, `thread_run`, `init`, `done`,
  `report_intermediate`, `report_cumulative`) are dead constants — see Feature 010.
- Status was derived from source inspection during registry bootstrap, not from a completed
  `/speckit.plan` → `/speckit.implement` cycle.

## Future Evolution Suggestions

- Reject `wasmer` / `wasmtime` at dispatch time with a clear "backend not implemented"
  message until Features 005 and 006 land, instead of failing later with a NULL call.
- Validate that the selected runtime descriptor has all mandatory vtable members populated
  before returning from `sb_load_wasm`, turning a latent crash into a startup error.
- Allow `--wasm-runtime` to accept a comma-separated list so one invocation can sweep
  several engines over the same workload (feeds Feature 013).
