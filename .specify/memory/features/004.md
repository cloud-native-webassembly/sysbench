# Feature Detail: WasmEdge Runtime Backend

**Feature ID**: 004  
**Name**: WasmEdge Runtime Backend  
**Description**: Integrates the WasmEdge SDK as a sysbench WASM backend covering load, validate, instantiate, and invoke.  
**Status**: Implemented  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

WasmEdge is the second working backend and the first proof that the Feature 002 abstraction
generalises beyond WAMR. It covers the engine lifecycle through the WasmEdge VM API —
configure, store, VM, load-from-buffer, validate, instantiate — and invokes exported
functions by name. Having a second independent engine behind the same vtable is what makes
cross-runtime comparison (Feature 013) meaningful rather than hypothetical.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. The lifecycle is
implemented and error paths clean up correctly, but three defects make this backend weaker
than WAMR:

1. `addr_app_to_native` and `addr_native_to_app` are never assigned on the sandbox
   (`src/sb_wasmedge.c:110-115`). Because the sandbox comes from `malloc`, those pointers
   hold indeterminate values, and any call through `sb_wasm_addr_app_to_native` would jump
   to garbage. Buffer-passing workloads are therefore unsupported here.
2. `sb_wasmedge_function_apply` passes `context` — the `sb_wasm_sandbox_context *` — as the
   first argument to `WasmEdge_VMExecute` (`src/sb_wasmedge.c:55`) instead of the
   `vm_context` it just unpacked on line 50. This is a type-confusion bug on the hot call
   path.
3. `sb_wasmedge_destroy` (`src/sb_wasmedge.c:137`) returns `SUCCESS` without deleting the
   VM, store, or configure contexts.

## Key Changes

1. Implemented the private context `sb_wasmedge_sandbox_context` holding
   `WasmEdge_ConfigureContext *`, `WasmEdge_StoreContext *`, `WasmEdge_VMContext *`.
2. Implemented `sb_wasmedge_create_sandbox` (`src/sb_wasmedge.c:74`) covering
   `WasmEdge_ConfigureCreate`, `WasmEdge_ConfigureAddHostRegistration` with
   `WasmEdge_HostRegistration_Wasi`, `WasmEdge_StoreCreate`, `WasmEdge_VMCreate`,
   `WasmEdge_VMLoadWasmFromBuffer`, `WasmEdge_VMValidate`, `WasmEdge_VMInstantiate`.
3. Implemented `sb_wasmedge_function_apply` (`src/sb_wasmedge.c:48`) marshalling one
   `WasmEdge_ValueGenI64` parameter and invoking via `WasmEdge_VMExecute`.
4. Implemented `sb_wasmedge_function_available` (`src/sb_wasmedge.c:34`) via
   `WasmEdge_VMGetActiveModule` + `WasmEdge_ModuleInstanceFindFunction`.
5. Implemented rollback-on-error in `create_sandbox` (`src/sb_wasmedge.c:116-130`), deleting
   any contexts already created before returning `NULL`.
6. Registered the `wasmedge_vm` descriptor with `load_module = NULL` and exposed
   `create_wasmedge_runtime()` (`src/sb_wasmedge.c:150`).

## Implementation Notes

- SDK surface used: `wasmedge/wasmedge.h`. WASI is registered as a host module, so workloads
  may use WASI imports.
- Execution mode is left to WasmEdge's internal default; no AOT compilation path is wired,
  so results reflect interpreted or engine-default execution only.
- `sb_wasmedge_function_apply` discards the return value — the commented-out line at
  `src/sb_wasmedge.c:58` shows a result read was intended but the `carrier` is never written
  back, so a workload cannot return data to the host on this backend.
- `sb_wasmedge_init` (`src/sb_wasmedge.c:66`) has an unreachable `error:` label with no
  corresponding `goto`; harmless but dead.
- Error reporting is inconsistent: some paths use `log_text(LOG_FATAL, ...)`, others
  `printf` / `fprintf(stderr, ...)` (lines 61, 101, 106), which bypasses sysbench's logger.
- Status was derived from source inspection during registry bootstrap, not from a completed
  `/speckit.plan` → `/speckit.implement` cycle.

## Future Evolution Suggestions

- Fix the `WasmEdge_VMExecute` first argument to use `vm_context`, and write the result back
  into `*carrier` so the backend reaches parity with WAMR on the call path.
- Implement `addr_app_to_native` / `addr_native_to_app` using the WasmEdge memory-instance
  API so buffer-passing workloads work here too (unblocks Feature 007 parity).
- Implement real teardown in `sb_wasmedge_destroy` — tracked as Feature 012.
- Route all diagnostics through `log_text` so failures are visible at the configured
  verbosity — tracked as Feature 018.
