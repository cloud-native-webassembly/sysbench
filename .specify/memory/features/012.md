# Feature Detail: WASM Resource Lifecycle Teardown

**Feature ID**: 012  
**Name**: WASM Resource Lifecycle Teardown  
**Description**: Release engine, module, instance, and heap resources on shutdown so long runs do not leak (DFR).  
**Status**: Draft  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

Every WASM backend currently acquires resources and never releases them. For a short
benchmark this is invisible; for the long, high-thread-count runs sysbench is designed for it
is a correctness and measurement problem — a leaking harness perturbs the very allocator
behaviour it is trying to measure, and drifting memory pressure makes late iterations
systematically slower than early ones.

This is the DFR (Design for Reliability) gap for the WASM layer: implement the teardown half
of the lifecycle that Feature 002's vtable already reserves space for.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. The gap is uniform across
the layer: `sb_wamr_destroy` (`src/sb_wamr.c:56`), `sb_wasmedge_destroy`
(`src/sb_wasmedge.c:137`), and `sb_wasm_op_done` (`src/sb_wasm.c:226`) all return `SUCCESS`
with empty bodies. No sandbox, module buffer, pooled heap, or engine context is ever freed,
and `wasm_runtime->destroy()` is never even called by the generic layer.

## Key Changes

1. Implement `sb_wasm_op_done` (`src/sb_wasm.c:226`) to iterate the `sandboxs` array,
   destroy each sandbox through a new vtable member, free the array, free the module
   `file_buffer`, and then call `wasm_runtime->destroy()`.
2. Add a `destroy_sandbox` member to `sb_wasm_runtime` (`src/sb_wasm.h:81-90`) so per-thread
   cleanup is dispatched per backend rather than guessed by the generic layer.
3. Implement WAMR teardown: `wasm_runtime_destroy_exec_env`,
   `wasm_runtime_deinstantiate`, `wasm_runtime_unload`, `wasm_runtime_destroy`, and `free`
   of the pooled heap allocated at `src/sb_wamr.c:111`.
4. Implement WasmEdge teardown: `WasmEdge_VMDelete`, `WasmEdge_StoreDelete`,
   `WasmEdge_ConfigureDelete`, mirroring the rollback path that already exists on the error
   branch at `src/sb_wasmedge.c:117-128`.
5. Move WAMR's `wasm_runtime_full_init` out of per-sandbox creation
   (`src/sb_wamr.c:124`) into process-wide init, so global runtime state is initialised and
   destroyed exactly once.
6. Add a leak check to the harness: run a fixed-event benchmark under
   `valgrind --leak-check=full` (or ASan) and assert no growth attributable to the WASM layer.

## Implementation Notes

- Ownership is currently undocumented: `create_sandbox` allocates both the private context
  and the `sb_wasm_sandbox`, and for WAMR also the pooled heap. Teardown must mirror that
  exactly, which is why a per-backend `destroy_sandbox` is preferable to generic `free`.
- The error paths in `sb_wamr_create_sandbox` `goto error` after partial acquisition without
  unwinding (e.g. heap allocated but module load failed), so failure leaks too — the same fix
  should cover both paths.
- Teardown ordering matters per SDK: WAMR requires exec-env destruction before
  deinstantiation; WasmEdge requires VM deletion before store and configure.
- This feature depends on Features 005 and 006 only insofar as those backends must implement
  their own teardown when written; it is not blocked by them.
- Verifying "no leak" requires a comparable before/after measurement, not merely a code
  review — per Constitution Principle VIII evidence discipline.

## Future Evolution Suggestions

- Add a long-soak benchmark mode (fixed duration, high thread count) to CI once teardown
  lands, as the regression guard for this class of defect.
- Report peak RSS alongside throughput so memory behaviour is part of the result set.
- Consider sandbox pooling/reuse across iterations as a separate measured configuration once
  lifecycle correctness is established.
