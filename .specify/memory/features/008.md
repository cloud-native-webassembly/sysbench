# Feature Detail: WASM Benchmark Workload Suite

**Feature ID**: 008  
**Name**: WASM Benchmark Workload Suite  
**Description**: A set of C-sourced WASM modules exporting `event`, compiled by WASI-SDK, used as the workloads under test.  
**Status**: Implemented  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

A runtime harness is useless without something to run. This feature is the workload side of
the WASM effort: seven small C programs compiled to `wasm32-wasi` modules, each exporting an
`event` function that the sysbench event loop invokes once per iteration. They are the
measurement subjects — the same module runs on every backend, which is what isolates the
runtime as the independent variable.

The workloads are deliberately shaped after realistic data-plane operations (string→number
conversion, string splitting, geometric distance, buffer summation) rather than synthetic
spin loops, so results speak to plausible embedding scenarios.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. Seven sources exist and
the build rules are present. Compliance note: no prebuilt `.wasm` binaries are checked in —
`src/wasm/.gitignore` lists the seven output names — which satisfies the constitution's
"no prebuilt binaries without source" rule. Weakness: four of the seven are stubs whose
`event` bodies return 0 without doing the work their comments describe
(`point_polygen_distance.c`, `split_string.c`, `string_to_double.c`, `string_to_int.c`), so
they currently measure call overhead only, not the advertised operation.

## Key Changes

1. Added seven workload sources under `src/wasm/`: `build_user_id.c`,
   `normalize_with_base.c`, `pass_data.c`, `point_polygen_distance.c`, `split_string.c`,
   `string_to_double.c`, `string_to_int.c`.
2. Added `src/wasm/Makefile.am` compiling each source with `${WASI_SDK_HOME}/bin/clang`,
   `--target=wasm32-wasi`, and `--sysroot=${WASI_SDK_HOME}/share/wasi-sysroot` (lines 17-18).
3. Established the export contract: `-Wl,--export=event` for every module (line 20), with
   `pass_data` additionally exporting `create_buffer` via a dedicated rule (line 44-45).
4. Fixed the module memory shape via link flags `-fPIC -z stack-size=8192
   -Wl,--initial-memory=65536 -Wl,--no-entry` (line 19), so modules are libraries rather
   than WASI commands.
5. Gated the whole workload build behind `if HAVE_WASM` (line 23) and conditionally added
   `src/wasm` to top-level `SUBDIRS` in `Makefile.am:31-33`.
6. Added `src/wasm/.gitignore` so compiled outputs are never committed.

## Implementation Notes

- Each source embeds the equivalent Python expression as a comment (e.g. `float(arg0)`),
  documenting intent — these comments are the only statement of what the workload should
  compute, since four bodies are unimplemented.
- `pass_data.c` is the richest workload: it exports `create_buffer`, participates in the
  Feature 007 handshake, and sums an `int32` array from sandbox memory.
- The workloads are declared as `bin_PROGRAMS` (line 24-31), which is an abuse of automake
  semantics — they are WASM artefacts, not host executables — and would attempt to install
  them into `bindir` on `make install`.
- The pattern rule `%: %.c` (line 41) plus the explicit `pass_data` rule use recipe lines
  indented with spaces in the source as read; automake/make require tab-indented recipes, so
  this is a build-correctness risk worth verifying on a clean tree.
- `WASI_SDK_HOME` is an unpinned external dependency; the compiled module bytes depend on
  the WASI-SDK/clang version, which affects comparability across machines (see Feature 016).
- `src/wasm/build.sh` provides a standalone single-file compile path outside automake.
- Status was derived from source inspection during registry bootstrap, not from a completed
  `/speckit.plan` → `/speckit.implement` cycle.

## Future Evolution Suggestions

- Implement the four stub workloads so they perform the operation their comments describe,
  or relabel them explicitly as call-overhead baselines.
- Reclassify the WASM outputs away from `bin_PROGRAMS` to a custom target so `make install`
  does not treat them as host binaries.
- Add a compute-heavy and an allocation-heavy workload so the suite covers more than
  data-marshalling cost.
- Record the WASI-SDK version alongside results so numbers from different toolchains are not
  compared silently.
