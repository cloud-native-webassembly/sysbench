# Feature Detail: Sandbox Resource Configuration

**Feature ID**: 010  
**Name**: Sandbox Resource Configuration  
**Description**: Environment-variable-driven heap, stack, thread, and buffer sizing for WASM sandboxes (DFCfg).  
**Status**: Implemented  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

WASM sandbox performance is dominated by how much memory it is given: heap size determines
allocator behaviour, stack size caps recursion depth, and buffer size sets the data-exchange
working set. A benchmark that cannot vary these cannot explore the performance surface, and a
benchmark that does not record them produces numbers nobody can reproduce.

This is the DFCfg (Design for Configuration) capability for the WASM layer: four tunables
with documented defaults, read from the environment at module-load time and applied to every
sandbox.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. All four tunables are read
and applied. The design gap is that they are environment variables only — unlike every other
sysbench knob, they are not `sb_arg_t` options, so they do not appear in `--help`, are not
validated, and are not echoed into the run report. That makes a run's memory configuration
invisible in its own output, which conflicts with the constitution's Measurement Integrity
principle.

## Key Changes

1. Defined defaults in `src/sb_wasm.h:112-115`: `WASM_STACK_SIZE` 8092,
   `WASM_HEAP_SIZE` 1 MiB, `WASM_MAX_THREAD_NUM` 16, `WASM_BUFFER_SIZE` 1 MiB.
2. Applied all four to the loaded module in `sb_wasm_op_init` (`src/sb_wasm.c:214-217`) via
   the `SB_SET_ENV_CONFIG` macro, which reads the same-named environment variable and falls
   back to the compiled default.
3. Carried the four values on `sb_wasm_module` (`src/sb_wasm.h:66-74`) so every backend's
   `create_sandbox` receives them uniformly.
4. Consumed `heap_size` and `stack_size` in the WAMR backend for pool allocation and
   instantiation (`src/sb_wamr.c:111-143`).
5. Consumed `buffer_size` in the Feature 007 `create_buffer` handshake
   (`src/sb_wasm.c:239`).
6. Sized the per-thread sandbox array from `sb_globals.threads` (`src/sb_wasm.c:219`).

## Implementation Notes

- `WASM_STACK_SIZE` defaults to 8092, an odd value that is almost certainly a typo for 8192;
  note that `src/wasm/Makefile.am:19` links guest modules with `-z stack-size=8192`, so host
  and guest stack expectations differ by four bytes.
- `max_thread_num` is read and stored but never used by any backend; sandbox count is driven
  by `sb_globals.threads` instead, so the tunable is inert.
- `WASM_HEAP_SIZE` is `1024 * 1024` as an unparenthesised macro; any use in a larger
  expression would misparse. Current uses are safe.
- Guest modules are linked with `-Wl,--initial-memory=65536` (64 KiB), which is far below the
  1 MiB host-side heap default — the effective limit is whichever the runtime enforces, and
  the mismatch is undocumented.
- No validation exists: a nonsensical value (zero, negative, larger than addressable) is
  passed through to the SDK.
- Status was derived from source inspection during registry bootstrap, not from a completed
  `/speckit.plan` → `/speckit.implement` cycle.

## Future Evolution Suggestions

- Promote the four tunables to real `sb_arg_t` options (`--wasm-heap-size`,
  `--wasm-stack-size`, `--wasm-buffer-size`) so they are discoverable, validated, and
  reported, while keeping the environment variables as fallbacks.
- Echo the effective resource configuration into the run header so every result set records
  the memory shape that produced it.
- Fix the 8092/8192 discrepancy and reconcile the guest `--initial-memory` value with the
  host heap default.
- Either use `max_thread_num` or remove it.
