# Feature Detail: Host-Sandbox Data Exchange

**Feature ID**: 007  
**Name**: Host-Sandbox Data Exchange  
**Description**: Packed address/size encoding plus app↔native translation for passing buffers between sysbench and a WASM module.  
**Status**: Implemented  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

The WASM call contract in Feature 002 allows exactly one `i64` in and one `i64` out. Real
workloads need to pass strings and arrays. This feature is the convention that resolves the
tension: a 32-bit sandbox-relative address and a 32-bit size are packed into the single
`i64` carrier, and the host translates that sandbox address into a native pointer to read or
write the payload.

It is the mechanism that lets a benchmark measure realistic data-passing cost rather than
only trivial scalar calls, and it is the reason the WASM layer can host workloads such as
string parsing and buffer summation.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. The encode/decode pair is
implemented on both sides of the boundary and is symmetric. Two limitations: only the WAMR
backend implements address translation, so the buffer path is single-runtime today
(the host-side write loop in `sb_wasm_op_next_event` is commented out at
`src/sb_wasm.c:152-157` with the note "currently only wamr support it"); and the host and
guest decoders disagree on pointer type — host `sb_wasm_addr_decode` writes `int32_t *addr`
(`src/sb_wasm.c:76`) while guest `wasm_addr_decode` writes `void **addr`
(`src/wasm/pass_data.c:9`).

## Key Changes

1. Implemented `sb_wasm_addr_encode(addr, size)` (`src/sb_wasm.c:72`) packing the address
   into the upper 32 bits and the size into the lower 32 bits of an `int64_t`.
2. Implemented `sb_wasm_addr_decode(val, addr, size)` (`src/sb_wasm.c:76`) as the inverse.
3. Implemented the guest-side mirror in `src/wasm/pass_data.c`: `wasm_addr_encode`
   (line 5) and `wasm_addr_decode` (line 9), so a module can both receive and return packed
   buffer references.
4. Added the vtable-dispatched translation wrappers `sb_wasm_addr_app_to_native`
   (`src/sb_wasm.c:81`) and `sb_wasm_addr_native_to_app` (`src/sb_wasm.c:85`).
5. Wired the `create_buffer` handshake into `sb_wasm_op_thread_init`
   (`src/sb_wasm.c:238-248`): if the module exports `create_buffer`, the host calls it with
   the configured buffer size, decodes the returned packed value, and stores the resulting
   sandbox address in `sandbox->buffer_addr`.
6. Made the handshake optional — a module without `create_buffer` logs a warning and
   continues (`src/sb_wasm.c:249-251`), so scalar-only workloads still run.

## Implementation Notes

- The packing scheme assumes a 32-bit WASM address space (wasm32), which holds for all four
  target runtimes today but would break under memory64.
- `sandbox->buffer_addr` is declared `int32_t` and logged with `%p` at `src/sb_wasm.c:246`,
  a format/type mismatch that will produce misleading output and compiler warnings.
- The per-iteration host write path is disabled: `sb_wasm_op_next_event` currently passes the
  bare `thread_id` as the carrier (`src/sb_wasm.c:159`) rather than a packed buffer
  reference. So while the handshake allocates a sandbox buffer, no benchmark presently
  measures host→sandbox writes per iteration.
- On WasmEdge the translation pointers are never assigned (Feature 004), so enabling the
  write path today would call through uninitialised memory on that backend.
- Status was derived from source inspection during registry bootstrap, not from a completed
  `/speckit.plan` → `/speckit.implement` cycle.

## Future Evolution Suggestions

- Unify the host and guest decoder signatures so both sides agree on the pointer type, and
  place the shared convention in one documented header.
- Re-enable the per-iteration buffer write once at least two backends implement translation,
  and gate it on a capability probe rather than a comment.
- Fix the `buffer_addr` logging to use an integer format specifier.
- Consider a bidirectional descriptor (address, size, direction) if workloads need to
  distinguish read-only from read-write buffers.
