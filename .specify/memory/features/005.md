# Feature Detail: Wasmer Runtime Backend

**Feature ID**: 005  
**Name**: Wasmer Runtime Backend  
**Description**: Integrate the Wasmer SDK as a sysbench WASM backend; currently a registered stub with no engine calls.  
**Status**: Draft  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

Wasmer is one of the four mainstream runtimes this fork targets. The scaffolding is in place
— configure detection, conditional build wiring, a runtime descriptor, and a factory
function — but no Wasmer API call has been written yet. Completing this backend is required
for the cross-runtime comparison story (Feature 013) to cover the full set of engines rather
than only WAMR and WasmEdge.

Because the descriptor registers successfully while leaving `create_sandbox` unset, this
feature is currently worse than absent: selecting `--wasm-runtime=wasmer` produces a crash
rather than an error message.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. `src/sb_wasmer.c` is 49
lines. All three implemented functions have empty bodies: `sb_wasmer_init`,
`sb_wasmer_destroy`, `sb_wasmer_load_module` (`src/sb_wasmer.c:33-35`). `wasmer.h` is
included but no Wasmer symbol is referenced anywhere in the file. Verdict: **stub**.

## Key Changes

1. Implement `sb_wasmer_init` to create the engine and store (Wasmer C API `wasm_engine_new`,
   `wasm_store_new`), replacing the empty body at `src/sb_wasmer.c:33`.
2. Implement `sb_wasmer_create_sandbox` — currently absent entirely — to compile
   (`wasm_module_new`) and instantiate (`wasm_instance_new`) the module per sysbench thread,
   and assign it to the descriptor at `src/sb_wasmer.c:37-44`.
3. Implement `function_apply` / `function_available` using `wasm_instance_exports` and
   `wasm_func_call`, marshalling the single `i64` carrier per the Feature 002 contract.
4. Implement `addr_app_to_native` / `addr_native_to_app` over `wasm_memory_data` so
   buffer-passing workloads (Feature 007) work on this backend.
5. Implement `sb_wasmer_destroy` with real teardown of instance, module, store, and engine.
6. Fix the return-type mismatch: `sb_wasmer_load_module` is declared to return
   `sb_wasm_module` by value (`src/sb_wasmer.c:35`) while the vtable member
   `sb_wasm_load_module_func` expects `sb_wasm_module *` (`src/sb_wasm.h:79`).
7. Implement or delete the five functions declared in `src/sb_wasmer.h:26-34`
   (`sb_wasmer_done`, `sb_wasmer_custom_command_defined`, `sb_wasmer_report_thread_init`,
   `sb_wasmer_report_thread_done`, `sb_wasmer_loaded`) that have no definitions.

## Implementation Notes

- Configure support already exists: `AX_CHECK_WASMER` (`m4/sb_wasm.m4:121-126`) provides
  `--with-wasmer`, discovers the SDK from `${WASMER_HOME}` or the `wasmer` binary on `PATH`,
  and emits `-lwasmer`. Build wiring exists at `src/Makefile.am:75`.
- Dispatch support already exists: `src/sb_wasm.c:103-107` maps `SB_WASM_RUNTIME_WASMER` to
  `create_wasmer_runtime()` under `#ifdef HAVE_WASMER`.
- Blocking hazard: with `create_sandbox` unset, `sb_wasm_op_thread_init` dereferences a NULL
  function pointer at `src/sb_wasm.c:231`. A guard in Feature 001/002 should land first so
  the failure is a diagnostic, not a segfault.
- No `scripts/wasmer/` directory and no `WASMER_OPTS` in `scripts/env.rc` exist, unlike WAMR
  and WasmEdge — the run/debug harness asymmetry must be closed as part of this feature.
- Wasmer supports multiple compiler backends (Cranelift / LLVM / Singlepass). Which one is
  selected materially changes benchmark results, so the choice must be explicit and
  reported, not left to the SDK default.

## Future Evolution Suggestions

- Expose the Wasmer compiler backend as a benchmark dimension once the basic path works.
- Add `scripts/wasmer/run.sh` and `scripts/wasmer/debug.sh` mirroring the WAMR scripts.
- Consider whether Wasmer's ahead-of-time `wasmer compile` artefacts should be benchmarked
  separately from JIT instantiation.
