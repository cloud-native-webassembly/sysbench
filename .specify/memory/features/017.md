# Feature Detail: WASM Layer Documentation

**Feature ID**: 017  
**Name**: WASM Layer Documentation  
**Description**: Architecture, backend contract, workload authoring, and usage docs for the WASM extension (DFDoc).  
**Status**: Draft  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

The repository has no `docs/` directory and its `README.md` is still the upstream sysbench
document — it describes the database and OS benchmarks and never mentions WASM. Everything
this fork adds is undocumented: how to build it, which runtimes work, how to write a workload,
what the backend contract is, and how to interpret results.

Constitution Principle I ranks documentation above testing precisely because this project is
worked on by agents that need accurate background context. Today that context must be
reconstructed by reading five C files and an m4 macro, which is both slow and error-prone.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. No `docs/` directory
exists. `README.md` headings cover only upstream topics (features, install, build, usage,
versioning) with no WASM section. The `--type` and `--wasm-runtime` options are undocumented
outside the option table in `src/sysbench.c`. No document states which backends are working
versus stubs, so the four-runtime goal reads as four-runtime support.

## Key Changes

1. Add a WASM overview document explaining the extension's purpose, the four target runtimes,
   and the current maturity of each — stating plainly that WAMR and WasmEdge work while
   Wasmer and Wasmtime are stubs.
2. Add a backend contract document describing the Feature 002 vtable: each member's meaning,
   which are mandatory, allocation ownership, and the steps to add a fifth runtime.
3. Add a workload authoring guide covering the `event` export contract, the optional
   `create_buffer` handshake, the packed address convention from Feature 007, and the
   WASI-SDK build flags.
4. Add a build-and-run guide covering `--with-wasm` plus per-runtime flags, the required
   `*_HOME` variables, and the `scripts/` harness entry points.
5. Add a results-interpretation note explaining what the numbers do and do not mean given
   execution-mode differences (ties to Feature 013).
6. Add a WASM section to `README.md` that links into the above rather than duplicating it.

## Implementation Notes

- Per Constitution Principle III, place documents by path so meaning derives from location —
  e.g. `docs/wasm/overview.md`, `docs/wasm/backend-contract.md`,
  `docs/wasm/workload-authoring.md`, `docs/wasm/build-and-run.md` — using lowercase
  kebab-case and reserving ALL-CAPS names for root-level conventional files.
- Per Constitution Principle I, documents must carry title, purpose, status, last-updated
  date, and related links, must cross-reference each other so navigation works through
  internal links, and must not restate implementation details that belong in the code.
- Per Constitution Principle II, documentation describes intended behaviour while code is
  authoritative for current behaviour. Where the two diverge — as with the four stub
  workloads and two stub backends — the document must say which parts are aspirational.
- `README.md` is the upstream file and carries upstream badges and install instructions;
  additions should be scoped to a clearly-marked fork section rather than rewriting it.
- The feature registry created by `/speckit.feature` is memory, not user documentation; it
  complements these documents but does not replace them.

## Future Evolution Suggestions
