# Feature Detail: Cross-Runtime Result Comparability

**Feature ID**: 013  
**Name**: Cross-Runtime Result Comparability  
**Description**: Record execution mode, SDK version, and configuration with every result so runtime comparisons are valid (DFP).  
**Status**: Draft  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

The purpose of this fork is to compare WASM runtimes against each other. That comparison is
only meaningful if the runs being compared differ in the runtime and nothing else. Today
nothing in the harness records or enforces that: SDK versions are unpinned, execution mode
(interpreter / JIT / AOT) is left to each engine's default and never reported, and resource
tunables come from environment variables that do not appear in the output.

The consequence is that two result sets can differ for reasons no one can reconstruct
afterwards. This is the DFP (Design for Performance) capability that makes the project's
headline claim defensible, and it is the direct operationalisation of Constitution
Principle VI (Measurement Integrity).

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. No provenance capture
exists anywhere in the WASM layer. Concretely: WAMR runs the classic interpreter by default
(`src/sb_wamr.c:124`), Wasmtime is JIT-first, and Wasmer's compiler backend is
SDK-default — so a naive WAMR-vs-Wasmtime comparison compares an interpreter against a JIT
without saying so. Additionally, `m4/sb_wasm.m4` performs no version check for any of the
four SDKs, and the run output contains no record of which SDK build was linked.

## Key Changes

1. Capture and report per-run provenance: runtime name, SDK version, execution mode, guest
   toolchain (WASI-SDK/clang) version, workload module identity, and the effective
   heap/stack/buffer configuration from Feature 010.
2. Expose execution mode as an explicit benchmark dimension (e.g. `--wasm-exec-mode`) rather
   than accepting each engine's default, with per-backend validation of supported modes.
3. Query the SDK version at run time where the API allows it, and record the configure-time
   discovered `*_HOME` where it does not.
4. Emit a machine-readable result record (JSON) alongside the human-readable report so
   cross-runtime comparisons can be assembled without re-parsing log text.
5. Add a sweep driver that runs one workload across every built runtime in a single
   invocation, producing a directly comparable result set (builds on Feature 011).
6. Define and document a stable reference workload plus the tolerance band used to judge
   whether a change altered performance, satisfying the constitution's 1% rule.

## Implementation Notes

- Execution-mode support differs per engine: WAMR offers classic-interp / fast-interp / AOT;
  Wasmtime offers Cranelift JIT plus AOT `.cwasm`; Wasmer offers Cranelift / LLVM /
  Singlepass; WasmEdge offers interpreter plus an AOT compiler. A single uniform mode enum
  will not map cleanly — the option must be per-backend validated with a documented mapping.
- JIT and AOT engines shift compilation cost out of the steady state, so first-call latency
  should be reported separately from steady-state latency or the comparison will flatter
  whichever engine front-loads work.
- The four workload stubs noted in Feature 008 currently measure only call overhead;
  comparisons drawn from them today say nothing about compute performance. Fixing that is a
  prerequisite for meaningful cross-runtime claims.
- Per Constitution Principle VIII, "runtime A is faster than B" must rest on comparable
  before/after evidence with identical workload, mode, and configuration — this feature
  exists to make that evidence collectable.
- Provenance capture must not enter the measured hot path; collect it at init and done only.

## Future Evolution Suggestions

- Store result records in a versioned schema so historical runs remain machine-readable as
  the harness evolves.
- Add per-iteration latency histograms broken out by runtime to the comparison output,
  reusing the existing `sb_histogram_*` primitives.
- Consider recording host provenance (CPU model, kernel, governor) since WASM engine
  performance is sensitive to all three.
