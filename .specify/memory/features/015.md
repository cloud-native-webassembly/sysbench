# Feature Detail: WASM Continuous Integration

**Feature ID**: 015  
**Name**: WASM Continuous Integration  
**Description**: CI jobs that configure, build, and exercise the WASM backends on every change (DFD).  
**Status**: Draft  
**Created**: 2026-08-01  
**Last Updated**: 2026-08-01

## Overview

CI currently validates the upstream database build and never touches the code this fork
exists to add. That means the WASM layer can break — or fail to compile at all — without any
signal. Given that the project's own build script does not actually enable WASM (Feature 009),
an unnoticed compile break is not hypothetical.

This is the DFD (Design for Deployment) gap: make the WASM configuration a first-class CI
target so the reliable-delivery leg of the agent work loop has something to stand on.

## Latest Review

Reviewed 2026-08-01 by code inspection during registry bootstrap. `.github/workflows/ci.yml`
defines two jobs, `build` and `build_mariadb`, both configuring with
`--with-mysql --with-pgsql`. Neither passes `--with-wasm` or any per-runtime flag, neither
installs a WASM SDK, and no step runs a WASM benchmark. The `Dockerfile` is likewise the
stock upstream recipe (ubuntu:xenial, MySQL/PostgreSQL only) and installs no WASM SDK.

## Key Changes

1. Add a CI job matrix that configures with `--with-wasm` plus each runtime flag, so a
   compile break in any backend fails the build.
2. Provision the SDKs in CI at pinned versions (see Feature 016), exporting the `*_HOME`
   variables that `m4/sb_wasm.m4` discovery expects.
3. Provision WASI-SDK so `src/wasm/` workload modules are built and the guest toolchain
   version is recorded.
4. Run the Feature 014 test suite in the WASM job, allowing documented skips where an SDK is
   intentionally absent.
5. Add a subset build (e.g. `--with-wasm --with-wamr` only) to prove the conditional wiring
   from Feature 009 genuinely tolerates missing SDKs.
6. Update the `Dockerfile` — or add a dedicated WASM development image — so the documented
   container path can build the WASM configuration.

## Implementation Notes

- Because `AX_CHECK_*` currently calls `AC_MSG_ERROR` when an SDK is missing
  (`m4/sb_wasm.m4`), a CI job that requests a runtime without provisioning its SDK will fail
  at configure time. Either provision every requested SDK or land the graceful-degradation
  fix in Feature 009 first.
- SDK provisioning is the expensive part: four runtimes plus WASI-SDK. Cache the installs by
  pinned version to keep job time reasonable.
- Wasmer and Wasmtime backends are stubs (Features 005, 006), so their jobs should assert
  "compiles and reports unsupported cleanly" rather than "runs a benchmark", until those
  features land.
- CI is a correctness gate, not a measurement environment: shared runners have noisy
  neighbours and variable CPU, so CI must not publish performance numbers or assert latency
  thresholds. Comparability runs belong on controlled hardware per Feature 013.
- The existing jobs pin `ubuntu-22.04` / `ubuntu-20.04`; the xenial-based `Dockerfile` is far
  older than either and may not support current SDK builds.

## Future Evolution Suggestions

- Add a scheduled soak job running the Feature 012 leak check, kept off the per-commit path.
- Publish build artefacts (the compiled `.wasm` workloads plus a manifest of SDK versions) so
  a measurement run on controlled hardware can consume exactly what CI built.
- Add a configure-matrix job that builds every subset combination of the four runtimes to
  guard the `AM_CONDITIONAL` wiring.
